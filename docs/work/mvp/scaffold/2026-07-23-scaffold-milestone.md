# Scaffold Milestone Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bootstrap `nodejs-sdk` from a docs-only repo to a buildable, lintable, testable, dual-JS/TS-consumable
state with one stub package (`@dexpace/core`) and zero domain code.

**Architecture:** A Bun-managed workspace (`packages/*`) with one package, `@dexpace/core`. Bun is the package
manager, test runner, and dev tool; the library itself still builds with plain `tsc` (never `Bun.build`) so its
output stays runtime-agnostic for consumers on Node, browsers, Deno, or Cloudflare Workers. Every quality gate
(lint, types, coverage, API-surface diff, package-health, audit) is wired as a blocking CI step against this stub
before any domain code is written.

**Tech Stack:** Bun (package manager, test runner), TypeScript 5.8+ (`tsc`, library build), gts + typescript-eslint
(lint), `@microsoft/api-extractor` (API surface diff), `publint` + `@arethetypeswrong/cli` (package health),
`@changesets/cli` (versioning), GitHub Actions (CI).

## Global Constraints

These apply to every task below; do not restate them per-task.

- TypeScript `^5.8` minimum (`erasableSyntaxOnly` requires it).
- Six mandatory `tsconfig` strictness flags, exact names: `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`,
  `noImplicitOverride`, `isolatedModules`, `verbatimModuleSyntax`, `erasableSyntaxOnly`. No more, no fewer.
- Lint caps, exact values: `max-lines-per-function` 70 (`skipComments: true`, `skipBlankLines: false`),
  `max-depth` 3, `max-params` 3.
- Banned by `erasableSyntaxOnly`: `enum`, runtime `namespace`, constructor parameter properties, `import =`.
- ESM only (`"type": "module"`), named exports only, kebab-case filenames.
- `@dexpace/core`'s `package.json` `dependencies` field is a committed, hard-empty object (`SEAM-1`) — never add
  a runtime dependency to it in this phase or any later one. Enforced mechanically, not just by convention:
  `scripts/verify-seam-1.mjs` (Task 6), blocking in CI (Task 8).
- `engines.node: ">=18.17"` on every publishable package, matching `tsconfig.base.json`'s `lib: ["ES2022"]`
  (`NFR-10`) — the two must move together.
- Coverage floor: 80% aggregate line coverage, enforced (not just reported) via `bunfig.toml`'s
  `coverageThreshold` (`NFR-5`).
- `exports` map has exactly one entry point (`"."`) with `types` + `import` conditions — no deep-import paths,
  no `require` condition (ESM-only library).
- `sideEffects: false` on every publishable package.
- Library packages build with plain `tsc` — `Bun.build` is reserved for services and must never appear in a
  package build script.
- Bun is pinned exactly via `.bun-version` (no range) — an explicit, reviewed bump only, never implicit.
- `gts lint` fails on unformatted code — no standalone Prettier or ESLint config; the one root `eslint.config.js`
  is the only overlay.
- Every `eslint-disable` carries a same-line reason (`@eslint-community/eslint-comments/require-description`).

## File Structure

```
.bun-version                              # exact Bun pin
package.json                              # root: workspaces, devDependencies, shared scripts
tsconfig.base.json                        # shared compiler options + the six strictness flags
eslint.config.js                          # single lint overlay (gts + typescript-eslint tiers + caps)
bunfig.toml                               # [test] coverage = true
.changeset/config.json                    # generated by `bunx changeset init`
.github/workflows/ci.yml                  # blocking CI: install, typecheck, lint, build, test, api, publish-lint, audit
scripts/verify-dual-consumption.mjs       # plain-JS/Node smoke import of the built package (no TS, no Bun)
scripts/verify-seam-1.mjs                 # asserts @dexpace/core's dependencies field stays empty
packages/core/package.json                # @dexpace/core manifest: exports map, empty dependencies, scripts
packages/core/tsconfig.json               # extends root base; adds outDir/rootDir
packages/core/tsconfig.build.json         # extends tsconfig.json; adds declaration/declarationMap/sourceMap
packages/core/api-extractor.json          # api-extractor config, report at packages/core/etc/core.api.md
packages/core/src/index.ts                # placeholder export: ping()
packages/core/src/index.test.ts           # bun:test for ping()
packages/core/etc/core.api.md             # generated, committed API report
```

`scripts/verify-dual-consumption.mjs` lives outside `packages/*` on purpose: it is not part of any package's own
source, so it is never type-checked or bundled as part of `@dexpace/core` — it exists solely to prove an
*external* plain-JS consumer can resolve and run the built package via `node_modules` workspace linking.

`engines.node` is deliberately absent here — it belongs on each *publishable* package (`packages/core/package.json`,

otherwise fail a gate the moment Phase 1 lands real code:

- `@types/bun` — supplies the `bun:test` module declaration. The `typecheck` script runs plain `tsc` (not Bun)

  suppressed).
- `fast-check` — the property-test library `sdk-design-nodejs/09` and `styleguide/typescript/11-testing.md`
  mandate for every codec/parser/serializer. Phase 1 has four such round-trip properties (MediaType, QueryParams,
  Headers, Request); the tests `import fc from 'fast-check'` and fail to run without it.
- `@eslint-community/eslint-plugin-eslint-comments` — provides `require-description` (wired in Task 2), which
  enforces the "every `eslint-disable` carries a same-line reason" rule the Global Constraints already state and
  which **NFR-7**'s "narrow, documented, re-enable-conditioned exception" clause depends on.

- [ ] **Step 3: Create `tsconfig.base.json`**

```jsonc
{
  "extends": "./node_modules/gts/tsconfig-google.json",
  "compilerOptions": {
    "composite": true,
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "lib": ["ES2022"],
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "erasableSyntaxOnly": true
  }
}
```

`module`/`moduleResolution: nodenext` (not `bundler`) because this is a *library* consumed by Node, browsers,
Deno, and Cloudflare Workers — `bundler` resolution is the Bun-*service* convention (`typescript-bun/01`), not
the library one (`typescript-bun/08`'s own `tsconfig.build.json` example uses `nodenext`). `lib: ["ES2022"]`
matches the `engines.node >=18.17` floor `sdk-design-nodejs/09` requires (**NFR-10**) — do not raise it without
also raising the declared floor.

`composite: true` is kept because `sdk-design-nodejs/02` builds the workspace on TypeScript **project references**,
which require it — even though there is only one package (and so no `references` array) until Phase 8. The
`typecheck` script runs `tsc -p … --noEmit` against this composite config; passing `--noEmit` on the CLI to
typecheck a composite project is supported (it is not the same as setting `noEmit: true` inside the config). At
Task 4 Step 6 — the first time `bun run typecheck` runs against real files — confirm it exits 0; if a future TS
release ever rejects the `--noEmit` + `composite` combination, switch the script to `tsc -b --emitDeclarationOnly`
or a dedicated non-composite `tsconfig.typecheck.json` rather than dropping `composite` (which the workspace shape
depends on).

- [ ] **Step 4: Create `bunfig.toml`**

```toml
[test]
coverage = true
coverageThreshold = 0.8
coverageSkipTestFiles = true
```

`coverageThreshold` is the enforcement half of `NFR-5` (an 80% aggregate line-coverage floor "wired into the
default build lifecycle") — `coverage = true` alone only *reports* coverage, it doesn't fail the build below the
floor. Both lines are required. `coverageSkipTestFiles = true` keeps the `*.test.ts` files themselves out of the
coverage *denominator* — `NFR-5`'s floor is about *source* coverage, and counting the test files (which are 100%
executed but are not the thing being measured) would distort the aggregate that gates the build.

- [ ] **Step 2: Write `eslint.config.js`**

```javascript
import tseslint from 'typescript-eslint';
import gts from 'gts';
import eslintComments from '@eslint-community/eslint-plugin-eslint-comments';

export default tseslint.config(
  ...gts,
  ...tseslint.configs.strictTypeChecked,
  ...tseslint.configs.stylisticTypeChecked,
  {
    plugins: {'@eslint-community/eslint-comments': eslintComments},
    languageOptions: {parserOptions: {projectService: true}},
    rules: {
      'max-lines-per-function': ['error', {max: 70, skipComments: true, skipBlankLines: false}],
      'max-depth': ['error', 3],
      'max-params': ['error', 3],
      // Explicit API surface — the design doc's gate table (Components §3) names both of these.
      // `allowExpressions: true` exempts inline callback arrows (test callbacks, `.map(e => ...)`)
      // so the rule only bites named/exported functions and methods, which is where the surface lives.
      '@typescript-eslint/explicit-function-return-type': ['error', {allowExpressions: true}],
      '@typescript-eslint/explicit-module-boundary-types': 'error',
      // Every `eslint-disable` must carry a `-- reason` (NFR-7's documented-exception clause).
      '@eslint-community/eslint-comments/require-description': 'error',
    },
  },
);
```

The two `explicit-*-types` rules are the "Explicit API surface" row of the scaffold design's gate table
(`sdk-design-nodejs/09`); `strictTypeChecked`/`stylisticTypeChecked` do **not** turn them on, so they must be
added by hand or the gate the checklist credits under **NFR-3** isn't actually wired. `require-description` is the
mechanism behind the Global Constraint that every `eslint-disable` names a reason — load-bearing now that Phase 1
uses a small number of documented `max-params` disables on its private, builder-internal constructors (see the
Phase 1 plan's Global Constraints).

**Two things to confirm when Step 3 first runs `bun run lint`, both of which fail the whole lint gate if wrong:**

1. **`...gts` must be a spreadable flat-config array.** gts v7 ships flat config, but confirm `import gts from
   'gts'` yields an array (some releases export `{ configs }` or a single object). If the spread throws, replace
   `...gts` with whatever gts documents for flat config at the installed version — do not drop gts.
2. **`projectService` + root-level files.** With the root `tsconfig.json` deleted in Step 1, files outside any
   package (`eslint.config.js`, `scripts/*.mjs`) belong to no TypeScript project, and `projectService: true` can
   error `… was not found by the project service`. If it does, add
   `parserOptions: {projectService: {allowDefaultProject: ['eslint.config.js', 'scripts/*.mjs']}}` (or scope
   `gts lint` to typed sources and lint the loose `.mjs` files with a separate untyped config block) — the
   `.mjs` verification scripts (Task 6) and this config file are plain JS and need no type-aware linting.

The `@eslint-community/eslint-comments` plugin is registered explicitly above. If gts already registers an
eslint-comments plugin under the *same* namespace key, flat config throws on the duplicate — in that case drop the
local `plugins` entry and rely on gts's registration, keeping only the `require-description` rule line. gts
historically bundled the unmaintained `eslint-plugin-eslint-comments` under the bare `eslint-comments` namespace,
which does **not** collide with `@eslint-community/eslint-comments`; verify at the installed version.

Expected: exits 0 — no `.ts` files exist under any `include` path yet, so there's nothing to flag. This step

- [ ] **Step 4: Write the SEAM-1 zero-dependency check**

`sdk-design-nodejs/02` specifies this exact mechanism: "a CI script parses [`@dexpace/core`'s `dependencies`
field] and fails the build the moment anything is added." `bun audit` (Task 7) checks for *vulnerabilities* in
